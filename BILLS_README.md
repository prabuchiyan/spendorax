# Spendorax Bills Flow Documentation

## 1. Introduction
The Bills feature in Spendorax is designed to manage both one-time payments and recurring subscriptions (e.g., EMIs, utility bills, subscriptions). The architecture uses a "Template-Instance" pattern where a single recurring bill generates specific monthly/weekly instances that the user actually pays.

## 2. Where and How a Bill is Created

### UI Component
Bills are created and edited via the `BillForm.js` component (typically rendered inside `BillFormScreen.js` or a modal).

### Database Layer
All bills are stored in the `bills` SQLite table.

### Creation Flow
1. **User Input:** The user fills out the bill details including Name, Amount, Due Date, Category, and optionally Recurrence (Daily, Weekly, Monthly, Yearly).
2. **Service Call:** The UI calls the `createBill(fields)` function in `src/services/bills.js`.
3. **Database Insertion:** The service inserts the primary bill record into the `bills` table.
   - If the bill is a one-time bill, this single record is all that is created.
   - If the bill is recurring (`is_recurring: 1`), this initial record acts as the **Template** (or Parent Bill).
4. **Initial Generation:** For recurring bills, `createBill` immediately calls `backfillBillOccurrences(newId)` to generate the upcoming instances (Child Bills) so the user can immediately see them on their calendar.

## 3. How Bills are Generated (Recurrence Logic)

Spendorax strictly separates the definition of a recurring bill from the actual instances you pay.

* **Template Bill:** The master record (`parent_bill_id IS NULL`). It defines the rules (e.g., $50 every month on the 5th).
* **Child Bills (Occurrences):** The actual bills that show up in your timeline (`parent_bill_id` points to the Template).

### The Scheduler Engine
Occurrences are generated by two primary functions in `bills.js`:
1. `backfillBillOccurrences(templateId)`: Generates instances for a specific template.
2. `runRecurringScheduler()`: A global background job that scans all active templates and ensures future instances are generated in advance.

### Generation Rules
- The engine calculates future dates based on `recurrence_type` (e.g., monthly) and `recurrence_interval` (e.g., every 1 month).
- **Idempotency:** To prevent duplicate bills for the same month, a unique `recurrence_occurrence_key` is generated for every child bill (e.g., `monthly-2023-10-05`). 
- The engine checks if a child bill with that key already exists for the parent before inserting a new one.

## 4. How a Bill is Paid

Bills in Spendorax are paid by linking them to actual Expense Transactions. This ensures your budgeting and cash flow remain perfectly synchronized with your bills.

### UI Component
Payments are initiated via `PayBillScreen.js` or Quick Actions on the `BillDetailScreen`.

### Payment Flow
1. **Initiation:** The user taps "Pay", selects a Source Account (e.g., Checking), and confirms the payment amount (which defaults to the bill amount).
2. **Service Call:** The app executes `markBillPaid(billId, paymentAmount, transactionId, sourceId)` in `bills.js`.
3. **Transaction Creation:** If the user is paying natively (no existing transaction provided), a new Expense Transaction is created in the `transactions` table, deducting money from the chosen Source Account.
4. **Linking (The Pivot Table):** A record is inserted into the `bill_linked_transactions` table. This many-to-many pivot table links the `transaction_id` to the `bill_id`. 
5. **Status Resolution:**
   - The bill's `paid_amount` is updated.
   - If `paid_amount >= amount`, the bill `status` is marked as `paid`.
   - If `paid_amount < amount`, the bill `status` becomes `partially_paid`.
6. **State Update:** `emitBillsChanged()` is fired, updating the Redux state and causing the UI to re-render.

## 5. Bill Maintenance and Statuses

To keep the UI accurate without requiring a server, Spendorax runs local maintenance routines.

* **Overdue Bills:** The `syncBillStatuses()` routine runs periodically. It scans all unpaid child bills. If a bill's `due_date` is in the past, its status is automatically flipped to `overdue`.
* **Skipped Bills:** Users can manually ignore a bill instance using `skipBill(billId)`. This marks the bill as `skipped` without deducting any money or creating a transaction.
* **Deleted Bills:** Bills use soft-deletes (`deleted_at`). Deleting a Template Bill will also cascade and soft-delete all unpaid future Child Bills.
